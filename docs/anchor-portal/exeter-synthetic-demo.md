# Exeter synthetic demo and acceptance

The fixture uses the exact label **Phillips Exeter Academy — Demo Building**. All records and illustrations are synthetic. They make no claim of actual Exeter service. The three facility zones depict classroom renovation, corridor renovation and restroom fit-out. Three sample completed reports each contain an original raster illustration. Two sample issues show open and resolved states, with an illustrative resolution photo.

## Isolation and provenance

`test/helpers/exeterPortalHarness.js` always launches its own temporary, loopback-only PostgreSQL database. It does not accept a database connection argument. It sets the disposable database before importing portal modules, never imports `server.js`, and explicitly disables application demo seeding. Fixture identities use `.invalid` email addresses and deliberately invalid password hashes; no login credentials are generated. A test-only session endpoint exists exclusively in the disposable harness. Do not mount that endpoint in the application.

Images are original deterministic PNG drawings generated by `illustrativePhoto()`, using JavaScript pixel construction and PNG encoding. No customer photos, remote images, real people, trademarks or claimed service photographs are used. Captions and embedded PNG descriptions label the images synthetic/illustrative. The drawings are facility-zone illustrations, not photographs of Exeter.

## Run

With repository dependencies and PostgreSQL `initdb`/`pg_ctl` installed:

```
node --test test/anchorPortalAcceptancePostgres.test.js
node scripts/demoExeterPortalLocal.js --disposable-local
```

The opt-in demo logs a loopback URL and local test-session instructions. It remains alive only until Ctrl-C, which closes the server and removes the database. It never seeds a supplied or deployed database. Publishing, production schema updates and real demo account setup remain separate approval gates.

The HTTP acceptance suite mounts real portal routes with ephemeral sessions. It checks persisted service reports/photos, client issue and resolution proof after a fresh session, tenant/location/visit denial, invalid/oversize image atomicity, duplicate submits and injected PostgreSQL photo-insert failure rollback. The test session endpoint is not a test of production password login.

## Browser acceptance

`node --test test/browser/anchorPortalBrowserAcceptance.test.js` uses Puppeteer with `CHROME_BIN` (default `/usr/bin/chromium`) against the same real routes and disposable PostgreSQL. It covers desktop report authoring, mobile issue/photo submission, literal rendering of hostile markup, resolution cancellation, In Progress, resolution photo persistence after reload, and unassigned users. All remote browser requests are blocked by the harness.

On 2026-10-14, the PostgreSQL acceptance suite passed 7/7 on the implementation checkout. The browser suite was authored and syntax checked, but execution was blocked before any page loaded: Chromium could not create its singleton Unix socket in the sandbox (`Operation not permitted`). No visual/mobile or browser end-to-end pass is claimed. Run this browser gate in an approved environment before walkthrough readiness is asserted. Production login and deployed data are outside this harness.
