## Exact operation and effects
The fixed server-side API is `prepareExistingCrm(pool, { programId, sourceMissionHash, admissions }, { env, now })` in `services/anchorScopedResumeCrmPreparation.js`. It is not a public HTTP route, scheduler activation or CLI credential-extraction workflow. A production execution route and the exact operator input must be reviewed before use; the current verified production tool route is Railway Data UI, and no arbitrary server invocation or credential extraction is authorized.

The input selects 1–5 exact, current, genuinely first-touch identities from an installed tenant-10 preparation-only grant. It binds the source mission's full payload hash, existing program/policy/scope, active operator, canonical managed Brevo sender/inbox, current provenance/ownership, literal-false review and installed historical quarantine. Email and research scopes must be disabled, with only explicitly selected preparation operations permitted. Missing or stale DB telemetry closes the operation.

The fixed adapter uses current locked CRM input and the existing deterministic Max/Paige/Emmett canonical executors. No Scout fallback, fresh search, enrichment, Bouncer/verification, LLM, live Brevo GET or provider dispatch occurs. Provider requests, LLM tokens and provider spend for this operation are zero. No pricing assumption is needed for a zero-call route; this says nothing about separately approved fresh inventory acquisition.

Durable effects are one irreversible preparation consumption record, a deterministic source-linked child mission, native stage/contribution/artifact audit records and the final preparation audit. The source mission is preserved. A failure after a canonical stage commit can leave a partial child and consumed budget; it cannot be retried by changing grant ID/day/caller operation ID. No automatic cleanup, refund or partial-child repair is implemented. The operation creates no execution approval, envelope, scheduled send, outbound reservation, contact admission or review-flag mutation.

## Budget accounting
Preparation item units count work, not distinct contacts. Drafting N identities consumes N item units and one operation. Later freezing those N identities consumes another N units and another operation. Therefore draft five then freeze five requires at least 10 preparation item units and two operations across the applicable daily/total caps. Canonical approval later consumes its own operation but zero item units. All counters are cumulative for the existing program and survive replacement grants, expiry, failures and day changes. Never silently replenish or refund them. The examples are arithmetic, not authorization; actual inputs/caps remain unset.

## Meaning of READY and readiness evidence
READY is a reviewable canonical artifact awaiting execution approval. It does not mean verified provider capacity or deliverability. SPF, DKIM, DMARC, blacklist and provider readiness remain UNKNOWN/unchecked. Native planning/governor numbers are preserved as planning outputs; bridge artifacts must explain that no provider or blacklist check ran, rather than repeating the legacy inferred “No blacklist concerns” assertion.

Later sending still uses the existing independent tenant/sender/inbox, canonical Brevo account/sender readiness, native governor/capacity/history, time window/spacing, execution approval, actual payload, identity/quarantine and final handoff checks. The Anchor readiness path calls evaluateCanonicalSenderReadiness then sendingReadiness.getBrevoState: a live Brevo domain must report authenticated=true and verified=true, and the exact sender must be active. That checks the provider-reported domain/sender state; it does not independently inspect DNS records or query a blacklist. The existing legacy snapshot infers some authentication fields from configured domain and does not itself prove DNS/blacklist verification. This bridge neither invents such evidence nor upgrades that legacy behavior to a verified assertion.
